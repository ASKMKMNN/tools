# 录屏视频批量处理备忘（FFmpeg）

> 用途：把 Win+G 录的竖版/大尺寸录屏，批量「居中裁成 16:9 → 缩到 1080p → 压体积 → 音量标准化」。
> 这份文档是给自己留的备忘，换电脑或几个月后重装时照着做即可。
> **当前脚本版本：v1.2（2026-11-10）**。窗口标题、窗口内三处、cmd 汇总第一行都带版本号，方便辨认手上是哪一版。
> 文件名也带版本号：`compress_mp4_v1.2.bat` / `使用说明_v1.2.md`，云端同名。
> 脚本用自身路径 `%~f0` 取文件，不依赖文件名；复制到视频文件夹后想改回短名也照常能跑。

## 2. 运行环境

- 系统：Windows 10 / 11（本项目在初代 Surface Book，i5-6300U 上验证）
- 依赖：**FFmpeg**（9.0.2 essentials 版本，含 libx264 / libx265）

### 当前机器上的安装位置

```
C:\Users\<用户名>\AppData\Local\Programs\ffmpeg\bin\
    ├─ ffmpeg.exe
    ├─ ffprobe.exe    ← 脚本用它回显成品分辨率
    └─ ffplay.exe
```

已写入**用户级 PATH**（注册表 `HKCU\Environment`，值类型 `REG_EXPAND_SZ`）。
验证方法：新开一个 cmd 窗口，执行 `ffmpeg -version`，能打印版本号即可。

### 换电脑时怎么重装（三步）

1. 下载 `ffmpeg-release-essentials.zip`（gyan.dev 官方构建），用 7-Zip / Bandizip 解压，
   得到形如 `ffmpeg-X.X.X-essentials_build\bin\ffmpeg.exe`
2. 把整个文件夹放到 `C:\ffmpeg`（路径别带空格和中文）
3. `Win+R` → `sysdm.cpl` → 高级 → 环境变量 → 用户变量 `Path` → 新建 → 填 `C:\ffmpeg\bin`
   → 确定，**重新打开** cmd 窗口验证

> 脚本自带兜底查找顺序：PATH → 脚本同目录 `ffmpeg.exe` → 脚本旁 `ffmpeg\bin\`
> → `%LOCALAPPDATA%\Programs\ffmpeg\bin\` → WinGet Links → `C:\ffmpeg\bin\`。
> 所以即使 PATH 没配好，把 `ffmpeg.exe` 丢到脚本旁边也能跑。

## 3. 怎么用（三步）

1. 把 `compress_mp4_v1.2.bat` 放到**视频所在的那一层文件夹**（不放子目录）
2. 双击 → 弹出「处理选项」窗口，选完点「开始压缩」
3. 等窗口显示「所有任务处理完毕」，看清成功/失败数后按任意键关闭

**选项窗口里的 4 组**（加粗 = 默认值，与 v1.0 行为一致，不选直接点开始即可）：

| 组 | 选项 | 说明 |
|---|---|---|
| 1 画面裁切 | 不变 / **16:9 居中剪裁** | 不变 = 保留原始比例，不裁 |
| 2 输出分辨率 | 沿用 / **1080P** / 720P | 沿用 = 不缩放；1080P/720P = 长边上限 1920/1280，本来就小的绝不放大 |
| 3 音频 | 沿用 / **标准化** | 沿用 = 直接复制原音轨（不重编码）；标准化 = loudnorm -16 LUFS + AAC 128k |
| 4 颜色 | 沿用 / **yuv420p** / 其它 | 下拉框里还有 yuv444p、yuv422p、yuvj420p、yuv420p10le、yuv444p10le，取舍见 5.5 |

> v1.2 起按钮上只写短档位（沿用 / 1080P / 720P），具体上限和每组细节写在卡片下方的小字里，
> 不再把长句塞进按钮，避免换行后被裁掉。

点「取消」或直接关窗口 = 一个文件都不处理。**输出位置**：同目录下的 `compressed\` 子文件夹，
文件名与原文件相同，**原文件不会被改动或删除**。

> 窗口默认**深色**，右上角「切浅色」可即时换成浅色；选中项与「开始压缩」统一为**中性灰**（v1.1 的青绿已去掉），两套配色都完整实现，只影响外观、不影响选项。
> v1.2 起按系统真实 DPI 等比放大布局（高分屏不再发虚），并按屏幕工作区自动限高，小屏上底部按钮不会被截。
> 版本号 `v1.2` 出现在窗口标题栏、标题右侧、底部信息行，cmd 汇总第一行也有「脚本版本」。
> 窗口打不开时（机器没有 PowerShell）会自动降级成文字菜单，5 秒不选按默认值继续，不影响使用。
> 固定不变的参数：CRF 28 / veryfast / 30fps / +faststart，见第 4 节。

## 4. 可调参数

选项窗口管上面 4 组；下面这 5 个仍在脚本开头的「可调参数」区，改一行即可，其余不用动。
（旧的 `NORM` / `MAXW` 已由窗口接管，脚本里的旧值只作为「窗口打不开」时的降级默认。）

| 变量 | 默认值 | 作用 | 怎么调 |
|---|---|---|---|
| `CRF` | `28` | 画质/体积平衡，0-51，越小越清晰越大 | 文字发虚改 `26`；想更小改 `30`；`32+` 会出糊块 |
| `PRESET` | `veryfast` | 编码速度 vs 压缩效率，不改画质档位 | 见下方说明 |
| `FPS` | `30` | 输出帧率 | 想保留 60fps 改 `60` |
| `ABR` | `128k` | 标准化时的音频码率 | 选「沿用」时走 `-c:a copy`，这个值不生效 |
| `LOGLEVEL` | `error` | 日志级别 | 排查怪文件时临时改 `warning` 或 `info` |

### 三种常用场景（现在都在窗口里选）

| 场景 | 窗口里怎么选 |
|---|---|
| ① 默认：1080p + 速度优先（推荐） | 16:9 裁切 + 1080P + 标准化 + yuv420p |
| ② 赶时间：720p，速度快 2.7 倍 | 把「输出分辨率」换成 720P |
| ③ 要看清小字：画质优先 | 「输出分辨率」选沿用（不缩放），再把脚本里 `CRF` 改成 `26` |

### 关于 PRESET（实测结论）

速度顺序：`ultrafast > superfast > veryfast > faster > fast > medium > slow > slower > veryslow`

- `veryfast` 是性价比拐点：同分辨率下比 `medium` **快约 1.7~1.9 倍，体积还略小**
- **绝对不要用 `ultrafast`**：只快 3.3 倍，但体积暴涨到 **3.8 倍**，纯亏
- `slow` 比 `medium` 再小 5%~10%，但耗时翻倍，130 个文件不值得

## 5. 核心原理

### 5.1 裁切 + 缩放（自适应，不用管源分辨率）

```bat
set "VF=crop=iw:'min(ih,round(iw*9/16/2)*2)'"
if not "%MAXW%"=="0" set "VF=%VF%,scale='min(%MAXW%,iw)':-2"
```

**第一步 `crop=iw:高:x:y`**

- 只写宽高、不写 `x/y` 时，ffmpeg 自动取 `(原尺寸-裁剪尺寸)/2`，即**居中**，所以上下不会偏移
- 宽 = `iw`：原宽度整幅保留
- 高 = `min(ih, round(iw*9/16/2)*2)` 的三重保险：
  - `iw*9/16`：按 16:9 反算该留多高
  - `÷2` 再 `round` 再 `×2`：**强制取偶数**。libx264 + yuv420p 要求宽高都是偶数，
    直接写 `iw*9/16` 会得到 1215 / 607.5 这种值，报 `height not divisible by 2` 整个文件就废了
  - 外套 `min(ih, ...)`：万一源比 16:9 还宽（超宽屏），只裁到原高度、不报错
- 单引号 `'...'` 是 ffmpeg 的表达式引用，用来保护表达式里的逗号（过滤器之间用逗号分隔）

**第二步 `scale='min(1920,iw)':-2`**

- 宽度取 `min(1920, 当前宽)`：**大的缩到 1920，本来就小的绝不放大**
- 高度 `-2` = 按原比例自动算，并保证偶数

### 5.2 实测自适应结果（已验证）

| 源分辨率 | 输出 |
|---|---|
| 2160×1440（3:2，本项目素材） | **1920×1080** |
| 3840×2160（4K） | 1920×1080 |
| 1080×1620（2:3 竖屏） | 1080×608（不放大） |
| 2560×1080（超宽屏 21:9） | 1920×810（不拉伸变形） |
| 1280×720（本来就小） | 1280×720（不放大） |

### 5.3 原始素材参数（备忘）

```
3840? 否 —— 实际为 2160 × 1440（3:2 横向）
30.04 fps / 视频 15975 kbps / 时长约 32 秒 / 约 64MB
音频 AAC 116 kbps 48 kHz 立体声
```

3:2 裁成 16:9 只切掉上下**各 112px**（1440→1216，占高度 15.5%），画面损失很小。

### 5.4 音量标准化

```bat
if /i "%NORM%"=="on" set "AF=-af loudnorm=I=-16:TP=-1.5:LRA=11"
```

- `I=-16`：目标平均响度 -16 LUFS（各视频平台通用量级）
- `TP=-1.5`：真峰值上限 -1.5 dBTP，**保证放大后不爆音**
- `LRA=11`：允许的动态范围

> **重要认知**：转码本身**不改变音量**（实测源与成品 mean_volume 都是 -53.1 dB）。
> 录屏时系统音量滑块偏低，录进去的电平就永久偏小，只能靠 `loudnorm` 重算响度补回来
> （实测 -53.1 dB → -15.3 dB）。音频**码率**只管清晰度，跟音量大小无关。

### 5.5 为什么默认 yuv420p（主因不是体积）

**主因是兼容性。**

- H.264 的主流档位（Baseline / Main / High）+ 8-bit 4:2:0 是硬件解码的事实标准：手机、微信、
  浏览器 `<video>`、QuickTime、智能电视、剪辑软件基本只保证这一档。4:2:2 属于 `High 4:2:2`、
  4:4:4 属于 `High 4:4:4 Predictive`、10-bit 属于 `High 10`，绝大多数硬解不支持，
  浏览器常常直接黑屏或提示「无法播放」。
- 录屏的画面特点让 4:2:0 几乎无损：文字锐度靠**亮度 Y**（全分辨率保留），色彩细节本来就少；
  4:2:0 只把色度 U/V 横竖各抽掉一半，肉眼基本看不出。
- 体积收益是附带的：4:2:0 的原始数据约为 4:4:4 的 50%（Y 全采、U/V 各 1/4），
  同 CRF 下编码后也明显更小；**10-bit 对 8-bit 源没有任何画质收益**，只是白涨体积。
- 固定写 `-pix_fmt yuv420p` 还有个「保险」作用：源若是 10-bit / 4:4:4 / RGB（部分录屏软件会出），
  不指定就可能原样带进成品，变成一个自己能放、发出去谁都放不了的文件。

所以下拉框里「其它」那几项，只在你明确知道成品要送去支持的地方时才选；
日常发微信 / 上传 / 存档，保持 `yuv420p`。

## 6. 实测性能数据（i5-6300U / 2 核 4 线程 / 2160×1440 源）

### 10 秒素材对比

| 配置 | 耗时 | 体积 | 分辨率 |
|---|---|---|---|
| medium + 原宽 | 23.3s | 4.59 MB | 2160×1216 |
| **veryfast + 1080p（默认）** | **11.7s** | **2.36 MB** | 1920×1080 |
| fast + 1080p | 22.9s | 2.73 MB | 1920×1080 |
| medium + 1080p | 20.2s | 2.69 MB | 1920×1080 |
| veryfast + 720p | 4.4s | 0.84 MB | 1280×720 |
| ultrafast + 原宽 | 4.3s | **10.04 MB** | 2160×1216 |

### 端到端（30 秒 / 60MB 素材）

```
耗时约 19 秒    60705 KB -> 6887 KB    1920×1080 @30fps（900 帧，时长不变）
```

### 130 个文件的预估

- **约 45 分钟**，总体积 **9 GB → 约 0.9 GB**
- 换成 `MAXW=1280`（720p）：约 17 分钟

### 硬件加速（实测：不要用）

| 方案 | 结果 |
|---|---|
| `h264_qsv`（Intel HD 520） | **5.9 秒，比 CPU 的 4.6 秒还慢**，体积还大 48%。另：qsv 会忽略 `-crf`，必须用 `-global_quality`，直接换 `-c:v` 参数会失控 |
| `h264_nvenc`（NVIDIA 940M） | **直接报错**。940M 是 GM108 核心，物理上没有 NVENC 编码单元，硬件不支持 |

结论：这台机器上纯 CPU 的 `libx264 + veryfast` 就是最优解，别折腾硬件编码。

## 7. 脚本行为细节

| 行为 | 说明 |
|---|---|
| 输出目录 | 脚本同目录的 `compressed\`，不存在会自动创建 |
| 命名 | 与原文件同名（`xxx.mp4`），扩展名统一小写 |
| 断点续跑 | **成品已存在就跳过**。中途 Ctrl+C / 断电后重新双击即可接着跑 |
| 临时文件 | 先写 `xxx.__tmp.mp4`，成功才 `move` 成正式文件名。失败时删掉临时文件，**不会留下半截坏文件冒充成品** |
| 失败日志 | `compressed\_失败清单.txt`，每次运行开头会重置 |
| 进度显示 | `[3/130] 正在处理: "文件名"` + ffmpeg 实时帧率 + 单文件体积变化 + **实际输出分辨率** |
| 特殊字符 | 支持空格、`&`、`!`、`()`、中文、`%` 等文件名（已实测） |
| 开头 | 汇总第一行显示「脚本版本 : v1.2」 |
| 结尾 | 汇总成功/失败数、总体积变化，然后 `pause` 停住窗口 |
| 选项窗口 | 双击先弹窗选 4 组参数；点「取消」或关窗口 = 不处理任何文件 |
| 窗口打不开 | 自动降级成文字菜单（5 秒不选用默认值），默认值与 v1.0 一致 |
| 一个滤镜都不用 | 裁切选「不变」+ 分辨率选「沿用」时，脚本填 `-vf null`（ffmpeg 空操作滤镜），保证命令合法 |

### 为什么脚本里有些"奇怪"的写法

| 写法 | 原因 |
|---|---|
| 不开 `enabledelayedexpansion` | 一旦开启，**文件名里的 `!`** 会被 cmd 当变量边界吃掉字符。所以计数一律用 `set /a`，变量靠 `set` + `call :子过程` 传递 |
| `echo ... "%NAME%"` 带引号 | 文件名里的 `&` 会被当成命令分隔符，加引号才安全 |
| 子过程用 `goto :LABEL` 而不是 `if (...)` 括号块 | **括号块里的 `%变量%` 在整块解析时就展开了**，会显示上一条文件的旧数据 |
| 文件必须是 GBK 编码 | 见第 8 节 |

## 8. 编码注意事项（改脚本前必看）

**`compress_mp4_v1.2.bat` 必须保存为 GBK(cp936) / ANSI 编码，且不带 BOM。**

- 存成 UTF-8 后，cmd 解析中文注释会**串行错乱**，报一堆「不是内部或外部命令」
- 加 `chcp 65001` 也救不回来（切换代码页会让 cmd 的文件读取位置错位）
- 用记事本另存时：**编码选「ANSI」**
- 用 VS Code 时：右下角编码 → Save with Encoding → `GBK`

**bat 末尾 `::PS ` 开头的那三百多行是选项窗口的 PowerShell 源码**，同样必须按 GBK 保存：
cmd 会把 `::` 开头的行当注释整行跳过，运行时由 PowerShell 按 cp936 读回、在 `%TEMP%` 生成临时
`.ps1` 再执行（用 `-ExecutionPolicy Bypass`，所以本机执行策略是 Restricted 也能弹窗）。
转成 UTF-8 会让窗口里的中文乱码；删掉这些行则只剩文字菜单降级。

窗口用 WinForms 自绘：卡片式布局、分段选择器、圆角控件、DWM 深色标题栏（调 `dwmapi.dll` /
`gdi32.dll`），下拉框用 `OwnerDrawFixed` 自绘以跟随深色/浅色。另调 `user32.dll` 声明
Per-Monitor-V2 DPI 感知：只放大坐标，字号仍用「点」交给系统换算——**字号若跟着乘 DPI 会放大两次，
把文字撑出按钮**（v1.1 的排版问题就是这样来的），再按屏幕工作区限幅。
原生调用整体包在 `try/catch` 里，老系统不支持时自动退成方角 + 系统标题栏，窗口照常能用。

覆盖文件后建议先拿 1~2 个视频试跑，确认窗口没有报错再批量。

## 9. 常见问题

**Q1：跑出来是 720p / 分辨率不对？**
① 选项窗口里选了 720P 或「沿用」→ 重跑时改回 1080P（v1.0 及更早的旧脚本窗口会有
`目标输出` / `音量处理` 两行，v1.1 起改为选项窗口）
② `compressed` 里有旧成品被「已存在」跳过 → **先删掉 compressed 文件夹**再跑

**Q2：声音很小 / 感觉被压缩了？**
转码不改音量（实测前后都是 -53.1 dB）。声音小是**录制时系统音量偏低**造成的。
脚本的 `NORM=on` 会统一拉到 -16 LUFS 修复（实测 -53.1 → -15.3 dB）。
若某个文件**完全没有声**，是录制时只勾了「仅麦克风/仅游戏音频」，脚本救不回来。

**Q3：某个文件失败了怎么办？**
看 `compressed\_失败清单.txt`。常见原因：文件损坏（`moov atom not found`）、
正在被录制/播放器占用、没有视频流。脚本会跳过它继续处理其余文件，不会中断。

**Q4：提示「没有找到 ffmpeg.exe」？**
把 `ffmpeg.exe` 复制到脚本同目录，或按第 2 节配 PATH 后**重新打开**窗口。

**Q5：窗口里中文是乱码？**
有两种：① 批处理自己的中文乱码 → 文件被存成 UTF-8 了，另存为 ANSI；
② 只有 ffmpeg 报错那几行里的**中文文件名**乱码 → 正常现象（ffmpeg 固定输出 UTF-8 而控制台是 GBK），
不影响脚本判断，`[失败]` 行和失败清单里的文件名都是准确的。

**Q6：处理速度越来越慢？**
i5-6300U 是 15W 芯片，长时间满载会降频。**插上电源**、任务栏电池图标选「最佳性能」、
垫高机器散热都能缓解。

**Q7：能不能只处理一部分文件？**
把不想处理的先剪切到别的文件夹；或者跑完后删掉对应的成品再重跑（会续跑）。
